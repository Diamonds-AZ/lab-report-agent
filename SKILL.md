# Lab Report Agent

Use this skill to turn a Word experiment report template into one or more completed lab reports while preserving the template structure.

## Core Architecture

The workflow has four layers:

```text
candidate extraction layer
-> GPT/Codex semantic planning layer
-> strict execution layer
-> audit decision layer
```

Scripts extract broad candidates and execute refined plans. GPT/Codex performs semantic decisions. Scripts must not decide final fill answers or final image slots.

Current boundary rule: after `.docx` is decomposed into `work/doc_structure.json`, scripts may only expose document-structure facts. They must not use keywords such as "如下图", "截图", "结果为", or long blanks to decide final text-fill positions, image insertion positions, or answer/question zones. GPT/Codex must make those semantic decisions.

## Current Formal Task Recommended Flow

Before starting a formal report task in a new conversation, read these operating documents:

- `docs/current_operating_policy.md` for workspace cleanup, identity defaults, dynamic image-count policy, current-run image isolation, text fill rules, and audit gates.
- `docs/smoke_test_status.md` for currently verified smoke tests and formal sample coverage.
- `docs/final_polish_policy.md` for final manual polish and delivery checks.
- `prompts/formal_lab_report_generation.md` for a reusable formal-report generation prompt template.
- `docs/known_issues_and_future_work.md` for limitations that should not be treated as stable production behavior.

Default formal-task posture:

- Treat every new conversation and existing workspace state as untrusted. For a new formal task, initialize the task explicitly with `scripts/prepare_new_task.py` (or an equivalent `prepare_task` phase) before `pre_images`.
- Only `prepare_new_task.py` / `prepare_task` may rebuild `configs/task.yaml`. `pre_images` must not silently overwrite `configs/task.yaml`.
- After template structure extraction, stop for first-stage task-understanding confirmation unless `work/task_directives.json` exists with `confirmed_by_user=true`.
- After `work/doc_structure.json` is generated, scripts may only produce a semantic judgment evidence packet. They must not make the final decision for `experiment_type`, `document_pattern`, `writing_mode`, `coverage_mode`, or `detail_level` by keyword matching.
- `scripts/infer_task_directives.py` writes `work/semantic_task_judgment_packet.md/json` and a pending `work/auto_task_directives.json`. Codex/GPT must read the packet, make the semantic judgment, rewrite `work/auto_task_directives.json` with real values, then run `scripts/render_task_confirmation.py <workspace>` and show that fixed-format first-stage confirmation to the user.
- First-stage confirmation format is fixed. It must use `work/task_understanding_confirmation.md` generated by `render_task_confirmation.py`; do not improvise a short summary. The fixed page includes experiment type, template pattern, report writing mode, coverage mode, detail level, image policy, identity policy, format policy, key template evidence, planned covered tasks, and examples of how the user can confirm or request changes.
- Confirmation Markdown files are audit artifacts, not user-facing substitutes. When `run_lab_report_task.py` writes `work/action_required.json` with `must_display_inline_to_user=true`, Codex must read `display_file` and present the confirmation content directly in the chat. Do not only send a file path, file card, or one-sentence summary.
- Confirmation is manual by default. Unless the user explicitly says full automation is allowed, Codex must not run confirmation scripts on the user's behalf and must not hand-edit `confirmed_by_user=true`.
- Valid manual confirmation requires `confirmation_source=explicit_user_reply` or `confirmation_source=user_reply`; valid automatic confirmation requires `confirmation_mode=agent_auto_allowed` and `confirmation_source=agent_auto_allowed_by_user`.
- Automatic confirmation must also record `auto_confirmation_grant_text`, copied from the user's explicit request for full automation. Without this grant text, `agent_auto_allowed_by_user` is invalid.
- `confirm_task_directives.py` and `confirm_image_plan.py` must be called with `--source explicit_user_reply` only after the user replies with confirmation. Use `--source agent_auto_allowed_by_user` only when the user clearly requested full automation / auto-confirmation / no intermediate questions.
- Keep `experiment_type`, `document_pattern`, and `writing_mode` independent:
  - `experiment_type` describes the domain/platform/software.
  - `document_pattern` describes the Word template structure.
  - `writing_mode` describes how this task should be completed.
  - Do not assume a database report must be `per_requirement`, or a network report must be `fill_blanks`.
- If no preset profile matches confidently, generate `work/discovered_profile_draft.yaml` and ask whether to use it only once or save it under `configs/profiles/discovered/`; never silently persist unknown types.
- After refined image planning, stop for second-stage image insertion confirmation unless `work/refined_image_plan.json` has `confirmed_by_user=true` with a valid confirmation source.
- Second-stage confirmation format is fixed. It must use `work/image_insertion_confirmation.md` generated by `build_image_insertion_confirmation.py`; do not improvise a short list. The table must show image number, zone type, human-readable insertion position, nearby anchor, covered requirements, image content, required visible code/result/error content, source policy, whether image-2 is mandatory, and risks/warnings.
- `work/image_insertion_confirmation.md` must exist and contain the confirmation table before `confirm_image_plan.py` may mark an image plan confirmed. A confirmed image plan without this file is invalid.
- For second-stage confirmation, Codex must paste the table into the conversation for review. The saved `work/image_insertion_confirmation.md` is only the durable record.
- Every refined text or image plan item must include `zone_type`, one of `answer_area`, `question_area`, `reference_material`, `identity_area`, or `unknown`. Formal report edits and image insertion should target `answer_area`. `question_area` and `reference_material` are forbidden unless the user explicitly asks to edit the question/reference content.
- If the user is not satisfied, they may reply in natural language. Do not force them to choose only "confirm" or "cancel". Record the feedback with `scripts/handle_user_feedback.py <workspace> record --stage auto --feedback-file <utf8_text_file>`, revise the corresponding semantic plan/directives, regenerate the fixed confirmation Markdown, show it again, and only then continue.
- Clean current task residue before starting, while preserving `assets/references/`.
- Do not modify the original template; copy it into workspace `input/`.
- After copying a template into `input/`, clear read-only file attributes before Word processing.
- Formal task output names default to `output/reports/<task_name>-完成版.docx`; `configs/task.yaml` may override this with `output_report_name`.
- Do not fill class, student ID, or name unless explicitly requested.
- Identity policy is explicit:
  - `preserve_existing_identity`: do not add identity information, but keep values already present in the source template.
  - `clear_identity_fields`: clear existing name/student ID/class fields when the user asks not to retain them.
  - `fill_identity_fields`: fill identity fields from an approved source.
- Let `refined_image_plan.json` decide image count dynamically.
- Use only the current run's `work/runs/<run_id>/generated_images/` as the insertion source.
- Require high-image-count confirmation when the threshold is exceeded.
- Run and inspect audit reports before delivery.
- Do not present a report as complete unless the post-image audit gate passes.
- Audit reports classify unresolved text as expected blanks, intentionally unchanged text, or real unresolved text.
- Audit reports summarize screenshot provenance through `image_source_summary`; do not describe generated or synthetic images as real screenshots unless their source is `real_screenshot`.
- If user requires image-2, set `image_mode=gpt_image_2_only` / `image_source_policy=gpt_image_2_only`; final inserted images must be recorded in `work/generated_images_manifest.json` with `declared_source=gpt_image_2`, `created_by=image_2`, `generation_mode=gpt_image_2_only`, and a matching `sha256`.
- In `gpt_image_2_only` mode, do not use PIL, HTML, matplotlib, dummy, placeholder, synthetic, script-rendered, legacy, or older-run images as substitutes.
- If `ACTION_REQUIRED_GENERATE_IMAGE_2_IMAGES` is emitted, Codex must call the `image_gen` tool for every item in `work/image_generation_plan.json` before `post_images`. This state must never be satisfied by local scripts, PIL, HTML rendering, dummy images, screenshots from older runs, or manual placeholders.
- After calling `image_gen`, save each PNG into the current run's `generated_images_dir` using the exact `output_filename`, then run `scripts/build_generated_images_manifest.py <workspace> gpt_image_2 image_2` and `scripts/validate_generated_images_manifest.py <workspace>`.
- Use final polish checks for command formatting, unresolved blanks, screenshot quality, and screenshot/text consistency.

## Core Rules

- Never modify the input template directly. Always operate on an output copy.
- `configs/task.yaml` is the task source of truth only after the current task has been explicitly initialized. Do not trust a leftover `configs/task.yaml` from a previous task.
- New formal tasks must not silently reuse old `work/current_run.json`, old `generated_images`, old `output/reports`, or old task startup audit state.
- In `first_run_test`, do not fill real name, student ID, class, or identity-derived screenshot content.
- Each run must use `work/runs/<run_id>/generated_images/`.
- `assets/generated_images/` is legacy/archive only and must never be used as an insertion source.
- All Chinese text, answers, report text, and image prompts must travel through UTF-8 files, not shell pipes or command arguments.
- Chinese paths, Chinese body text, and complex JSON must not be embedded in PowerShell here-strings, PowerShell pipes, `python -c`, or temporary inline Python snippets. Write them to UTF-8 files and pass only paths/control arguments.
- If output introduces new `???` or `�`, treat the report as polluted and regenerate from a clean template.
- When `fill_identity_fields=false`, do not fill name, student ID, class, or identity-derived screenshot content.
- Optional `output_report_name` in `configs/task.yaml` overrides the default report filename.
- Image generation plans should carry `image_source` with one of `gpt_image_2`, `synthetic_hcl`, `synthetic_datagrip`, `manual_provided`, `real_screenshot`, or `unknown`.

## Semantic Text Planning

Text filling uses a two-step contract:

```text
work/doc_structure.json
-> work/draft_text_fill_candidates.json (semantic materials only)
-> GPT/Codex semantic review
-> work/refined_text_fill_plan.json
-> apply_text_fill_plan.py
```

Rules:

- `extract_text_fill_candidates.py` only produces structure facts for GPT/Codex semantic planning. It must not decide final text-fill slots.
- `refined_text_fill_plan.json` must be produced by GPT/Codex semantic planning.
- Each refined text item must include `zone_type`. Do not fill or rewrite `question_area` or `reference_material` unless `explicitly_allowed_question_area_edit=true` and the user explicitly requested that behavior.
- Scripts must not copy or rename draft candidates as refined plans.
- If `fill_text=true` and `refined_text_fill_plan.json` is missing, stop with `ACTION_REQUIRED`.
- `apply_text_fill_plan.py` only reads `refined_text_fill_plan.json`.
- If the user asks to change text tone, length, code, result wording, or summary, record feedback at `text_plan`, update `work/refined_text_fill_plan.json`, and regenerate the user-facing preview or relevant confirmation before continuing.
- Do not append answers when no in-place blank target is found.
- Do not write answers on the next line or with prefixes such as `应填入：`, `答案：`, `原因：`, or `说明：`.
- Multi-slot fills must include `slot_index`, `left_context`, and `right_context`.
- Currently supported text execution strategies are `replace_placeholder`, `replace_blank_spaces`, `fill_after_prefix`, and `fill_table_cell`.
- `insert_after_anchor`, `replace_paragraph_content`, and `merge_following_explanation` are reserved but not stable; unsupported strategies must be recorded as unresolved instead of appended.

## Semantic Image Planning

Image planning uses a separate contract:

```text
work/doc_structure.json
-> work/draft_image_slot_candidates.json (semantic materials only)
-> GPT/Codex semantic review
-> work/refined_image_plan.json
-> work/image_generation_plan.json
```

Rules:

- `extract_image_slot_candidates.py` only produces structure facts for GPT/Codex semantic planning. It must not decide final image slots from words like "下图", "如下图", "截图", or nearby blank paragraphs.
- GPT/Codex must first classify planned targets as `answer_area`, `question_area`, `reference_material`, `identity_area`, or `unknown`.
- Do not insert images into long task requirements, reference explanations, or question text merely because those areas mention "下图" or "如下图".
- If a template contains a divider such as "实验报告模板", prefer image/text targets after that divider unless the user explicitly asks to modify earlier reference material.
- `build_image_prompts.py` must only derive prompts from `refined_image_plan.json`.
- `build_image_prompts.py`, `validate_plans.py`, and `insert_report_images.py` must reject required image items that target `question_area` or `reference_material` unless `explicitly_allowed_question_area_image=true`.
- If the user asks to move, remove, add, or change an image, record feedback at `image_plan`, update `work/refined_image_plan.json`, regenerate `work/image_insertion_confirmation.md`, and ask for confirmation again before generating images.
- Image count is dynamic: `expected_image_count` equals required items in `refined_image_plan.json`.
- Do not treat all empty tables as final image slots without GPT/Codex refined planning.
- `post_images` must validate that `current_run.json`, `image_generation_plan.json`, and `generated_images_dir` share the same `run_id`.
- Missing images fail immediately. Do not substitute historical images.
- After calling image_gen/image-2, copy each generated PNG into `image_generation_plan.json.generated_images_dir` and rename it exactly to the item's `output_filename` before running `post_images`.
- `post_images` may read only `work/runs/<run_id>/generated_images/`. It must not read `assets/generated_images/`, `output/images/`, `.codex/generated_images/`, or any older run directory.
- If `expected_image_count` exceeds `image_count_policy.confirm_threshold`, create `work/image_count_confirmation.json` after user approval. It must match the current `run_id`, `expected_image_count`, `confirm_threshold`, `generated_images_dir`, and plan fingerprint. Do not bypass confirmation by editing `task.yaml`.
- Current image insertion supports table-cell slots via `target_table_index`.
- Current image insertion also supports the minimum non-table `paragraph_blank_region` layout: use `target_anchor` plus `target_block_range` to place the image into the blank paragraph region after the anchor.
- Other non-table `layout_type` values are reserved for future support and must be recorded as unresolved instead of inserted randomly.
- Table-cell image insertion must allow the target table row to expand before inserting screenshots. Fixed row heights must be cleared where possible so screenshots are visible instead of cropped.
- Image quality checks are warning-only by default. Dark command-line or console screenshots are valid; warn only for clearly broken images such as almost pure black/white, extremely low information, tiny files, or very low resolution.

Image count policy defaults:

```yaml
image_rules:
  image_count_policy:
    warn_threshold: 8
    confirm_threshold: 12
    hard_limit: 40
```

## HCL Reference Images

- HCL reference images live under `assets/references/hcl/`.
- If references exist and the resolved experiment type is `network_hcl`, run `analyze_references.py` before building prompts.
- The analyzer writes both `work/reference_analysis.md` and `work/reference_analysis.json`.
- Reference images are style-only: window layout, menus, toolbar, topology canvas, device icons, connection style, CLI window style, fonts, and colors.
- Do not copy reference project names, paths, commands, device names, personal information, or watermarks.
- Do not inject HCL reference analysis into DataGrip, IDEA, VS Code, or other non-HCL prompts.
- HCL prompt style should distinguish topology screenshots from console screenshots: topology prompts should match the Chinese HCL grid canvas, left dark palette, blue labels, and right `抓包接口列表` / `拓扑汇总` panels; console prompts should match the large black H3C console window with white monospace text and `<H3C>` prompt.

## Execution Flow

### pre_images, first pause: semantic planning

```text
run_lab_report_task.py <workspace> pre_images
-> init workspace
-> create run
-> resolve input
-> write current_task_context.json
-> analyze template
-> extract doc structure
-> infer task directives
-> ACTION_REQUIRED_CONFIRM_TASK_UNDERSTANDING unless task_directives confirmed
-> extract text fill candidates
-> extract image slot candidates
-> ACTION_REQUIRED: refine semantic plans
```

After the first confirmation, Codex/GPT must write or confirm:

```text
work/task_directives.json
```

Then `pre_images` continues and Codex/GPT must write:

```text
work/refined_text_fill_plan.json
work/refined_image_plan.json
```

### pre_images, second pause: image generation

After refined plans exist:

```text
validate_plans.py semantic
-> build image insertion confirmation
-> ACTION_REQUIRED_CONFIRM_IMAGE_INSERTION_PLAN unless refined_image_plan confirmed
-> analyze references
-> build image prompts
-> prepare image generation
-> validate_plans.py image_generation
-> ACTION_REQUIRED: generate images
```

Generated images must be copied into the plan's `generated_images_dir` with each item's `output_filename`.
If `gpt_image_2_only` is active, `pre_images` emits `ACTION_REQUIRED_GENERATE_IMAGE_2_IMAGES` and writes `work/image_2_generation_todo.md`. Codex must call `image_gen` for each planned image, save the output with the exact `output_filename`, and then write `work/generated_images_manifest.json`; `post_images` must validate the manifest before insertion.

### post_images

```text
run_lab_report_task.py <workspace> post_images
-> validate run and plans
-> validate first-stage and second-stage confirmations
-> validate generated_images_manifest.json when image-2 is required
-> apply refined text fill plan
-> insert images by target_table_index or paragraph_blank_region
-> build requirement coverage report
-> audit report
```

## Audit

`audit_report.py` writes:

```text
work/batch_check_report.md
work/batch_check_report.json
```

Hard-fail conditions include:

- Missing images.
- Image count mismatch.
- Legacy image use.
- `run_id` mismatch.
- Invalid high-image-count confirmation when confirmation is required.
- Confirmed table-cell crop risk where a fixed row height could not be cleared.
- Output introduces new `???` or `�`.
- Missing refined plan but execution proceeded.
- Important blanks or image slots unresolved and not recorded.
- Forbidden answer prefixes.

After every `post_images`, inspect:

- `work/batch_check_report.md`
- `work/blank_fill_audit.md`
- `work/encoding_report.md`

The batch audit should expose expected/generated/inserted image counts, `generated_images_dir`, missing images, unexpected images, legacy-image use, high-image-count confirmation status, suspected cropped images, image quality warnings, unresolved text, unresolved image slots, and encoding pollution.

## Batch Status

Batch report generation and identity field filling are later-stage capabilities. Do not treat `build_student_reports.py` as stable production behavior until templates provide explicit identity anchors or a field map. `first_run_test` remains identity-free by default.
