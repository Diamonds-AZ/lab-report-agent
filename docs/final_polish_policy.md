# Final Polish Policy

This document defines the final manual polish and audit pass before a completed report is delivered. It is currently a documentation rule set, not a complex automatic repair script.

## Command Formatting

Check for command text issues such as:

- Missing spaces, for example `interfaceGigabitEthernet`.
- Parameter collisions, for example `address-group 1no-pat`.
- Incorrect view prompts, such as interface commands shown under the wrong router or wrong view.
- Commands that belong to one experiment phase appearing in another phase.

## Duplicate Titles

Check for repeated labels such as:

- `步骤六：步骤六：`
- duplicated section headings,
- repeated figure labels introduced by generation or filling.

## Typos

Check template and generated text for obvious typo remnants, for example:

- `惊醒 CHAP 验证` should be `进行 CHAP 验证`.
- `江 ACL` should be `将 ACL`.

Avoid broad rewrites. Fix only clear typos or report them for user review.

## Unfilled Blanks

Check for unresolved blank indicators:

- long underline runs,
- suspicious consecutive spaces,
- `其结果为`,
- `原因是`,
- `请补充完整命令`,
- incomplete command prompts.

Important command blanks should be filled in place when possible.

## Identity Fields

Check that identity policy was followed:

- class,
- student ID,
- student name,
- student ID or name in the filename,
- screenshot watermark requirements.

When identity filling is disabled, these fields must remain blank or untouched.

## Screenshot Quality

Check whether screenshots:

- display the intended content completely,
- are not cropped,
- are not too blurry,
- are not almost pure black or pure white,
- contain enough useful information,
- match the expected platform such as HCL, DataGrip, IDEA, or VS Code.

Dark command-line screenshots can be valid. Darkness alone is not a failure.

## Screenshot And Text Consistency

Check semantic consistency:

- If text says Basic NAT, the screenshot must not show Easy IP.
- If text says CHAP, the screenshot must not show PAP.
- If the figure is for an interface status check, the screenshot should show an interface status command.
- Figure content should match nearby text, table slot, and step context.

## Command Completion Positions

For locations asking for command completion:

- Do not rely only on screenshots.
- Fill the command text in the original blank when the template provides an in-place blank.
- Use screenshots as evidence that the command was executed.

## Delivery Gate

Before final delivery, inspect:

- `work/batch_check_report.md`
- `work/blank_fill_audit.md`
- `work/encoding_report.md`

Do not present a report as complete if hard-fail audit conditions remain.

The batch audit should be readable without opening JSON. Confirm:

- `final_status` is `PASS` unless the user is intentionally receiving an action-required draft.
- `output_report` uses `<task_name>-完成版.docx` or the explicit `output_report_name`.
- `image_source_summary` is present and does not mislabel generated or synthetic screenshots as real screenshots.
- `expected_blank_count`, `intentionally_unchanged_count`, and `real_unresolved_text_count` are separated.
- Identity blanks are expected only when identity filling is disabled or the user requested blanks.
- `real_unresolved_text_count` is zero before delivery.

## Confirmation Quality

Before delivery, also inspect:

- `work/task_understanding_confirmation.md`
- `work/image_insertion_confirmation.md`

First-stage task understanding must be confirmed after GPT/Codex semantic judgment, not while fields are still `pending_gpt_semantic_judgment`.

The first-stage confirmation must be the fixed page generated by `scripts/render_task_confirmation.py`. It should be understandable to a non-technical user and must show task goal, experiment type, document pattern, report filling/writing mode, coverage mode, detail level, image policy, identity policy, format policy, evidence from the template, planned covered tasks, and any uncertain points. A short improvised summary is not acceptable.

The second-stage image confirmation must be the fixed Markdown table generated by `scripts/build_image_insertion_confirmation.py`. It must show insertion positions, nearby anchors, covered requirements, image content, required visible code/result/error content, source policy, whether image-2 is mandatory, and examples of how the user can request changes.

## Question And Answer Zone Check

Before delivery, verify that refined text and image plans include `zone_type`.

Images and generated answer text should land in `answer_area`, not in `question_area` or `reference_material`.

Long requirement descriptions often contain phrases such as `下图`, `如下图`, or `观察`; these are not sufficient evidence that the report should insert a new image there. If an explicit answer section such as `实验报告模板`, `程序流程图`, `实验现象`, or `实验结果展示` exists later in the document, prefer that area.

Treat any unapproved image insertion or text rewrite in `question_area` / `reference_material` as a delivery blocker.

## User Feedback Closure

Before delivery, check `work/latest_user_feedback.json` if it exists.

If its status is `pending_revision`, do not deliver the report. Revise the relevant plan, regenerate the fixed confirmation Markdown, get approval, and mark the feedback resolved through `scripts/handle_user_feedback.py`.

If the user requested changes after viewing a draft report, the final response should summarize how those changes were applied.

## Confirmation Display Check

If the run stopped at an action-required confirmation gate, inspect `work/action_required.json`.

When `must_display_inline_to_user=true`, the confirmation content from `display_file` must have been shown directly in the chat. A path, file card, or one-sentence summary is not enough.
